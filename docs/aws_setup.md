# AWS Setup — Credit Risk Data Platform

This document tracks every step taken to set up the AWS side of the
project, in the order it was actually done — including manual console
steps later formalized in Terraform, and issues encountered along the way.

## 1. Account and IAM setup

- Created a new AWS account (Free Tier)
- Set a monthly budget alert (Billing → Budgets) to avoid unexpected costs
- Created a dedicated IAM user (`terraform-admin`) instead of using root
  credentials for daily work — best practice, root is reserved for
  account-level actions (e.g. granting IAM permissions)
- Attached `AdministratorAccess` to `terraform-admin` for this learning
  project. **Note for production context**: in a real team environment,
  Terraform's execution role should use least-privilege scoped policies
  instead — `AdministratorAccess` here is a deliberate simplification for
  a solo learning project, not a recommended production pattern
- Generated programmatic access keys for `terraform-admin`, configured
  locally via `aws configure` (region: `eu-west-1`)

**Issue encountered**: initial `terraform apply` failed with
`AccessDenied` on `s3:CreateBucket`, even though `AdministratorAccess` had
supposedly been attached. Root cause: the policy attachment during user
creation hadn't actually completed. Fixed by re-attaching the policy from
the console (root login) and verifying with
`aws iam list-attached-user-policies`.

## 2. Infrastructure (Terraform)

Provisioned via `infra/` (see `main.tf`, `variables.tf`, `outputs.tf`):

- 3 S3 buckets (Medallion layers): raw, silver, gold — versioning enabled,
  AES256 encryption, public access blocked, lifecycle rule on raw
  (Standard → Standard-IA after 30 days)
- IAM role `credit-risk-platform-glue-role` for Glue, scoped to only this
  project's S3 buckets (least privilege) plus the AWS-managed
  `AWSGlueServiceRole` policy
- Glue Data Catalog database: `credit_risk_platform_db`

Resulting bucket names (suffix is random, generated by Terraform):
- `credit-risk-platform-raw-385ac098`
- `credit-risk-platform-silver-385ac098`
- `credit-risk-platform-gold-385ac098`

## 3. Raw data upload to S3

Uploaded both source datasets to the raw layer, one prefix per source:

```bash
aws s3 cp data/gmsc.csv s3://credit-risk-platform-raw-385ac098/gmsc/gmsc.csv
aws s3 cp data/lending_club.csv s3://credit-risk-platform-raw-385ac098/lending_club/lending_club.csv
```

Total size: ~1.14 GB (7.5 MB GMSC + 1.13 GB Lending Club) — comfortably
within the 5 GB S3 Free Tier allowance.

**Note on versioning and cost**: since versioning is enabled on all
buckets, re-uploading the same file creates a new version instead of
overwriting — old versions still count toward storage. Checked via:
```bash
aws s3api list-object-versions --bucket credit-risk-platform-raw-385ac098
```
No duplicate versions accumulated in this case, but worth monitoring
during iterative work.

## 4. Glue Crawler — schema discovery

Created manually via the AWS Glue console (Crawlers → Create crawler),
later formalized in Terraform (`infra/glue_crawler.tf`) and imported into
Terraform state to avoid recreating it:

```bash
terraform import aws_glue_crawler.raw_crawler credit-risk-raw-crawler
```

Configuration:
- Source: S3, two targets (`gmsc/` and `lending_club/` prefixes)
- IAM role: the existing `credit-risk-platform-glue-role` (no new role
  created)
- Target database: `credit_risk_platform_db`
- Table prefix: `raw_` (resulting tables: `raw_gmsc`, `raw_lending_club`)
- Schedule: on demand (no continuous data arrival to justify scheduling)

**Issue encountered — CSV header misdetected**: the crawler's CSV
classifier didn't recognize the first row as a header for `raw_gmsc` (all
columns came back named `col0`, `col1`, ...). This happens when Glue's
heuristic can't confidently distinguish a header row from a data row (e.g.
when the first column is a plain numeric index). Fixed by manually adding
the table property `skip.header.line.count = 1` so Athena/query engines
skip the header row when reading data.

Full column renaming (from `col0`/`col1` to real names) was **not** done
at this stage — deferred to the Databricks/PySpark transformation step,
where the schema mapping logic already exists from local exploration
(see `docs/feature_engineering.md`). The Glue table schema here only
needed to be "good enough" to verify the crawler worked via Athena.

**Note on future crawler runs**: `schema_change_policy` in Terraform is
set to `LOG` for both update and delete behavior, so a future re-run of
the crawler won't silently overwrite the manual `skip.header.line.count`
fix.

## 5. Athena — verification query

Configured a query result location (required before any query can run):
```
s3://credit-risk-platform-gold-385ac098/athena-query-results/
```

Verified the crawler's schema inference with:
```sql
SELECT * FROM raw_gmsc LIMIT 10;
```

**Note on scope**: Athena is used here only as a quick verification tool
to confirm the Data Catalog schema is queryable — it is not part of this
project's main data flow, which continues through Databricks. Athena does
appear in the Cerved job requirements, so this hands-on check is enough to
speak to it in an interview without building a full pipeline around it.

**Note on cost**: Athena bills per data scanned (~$5/TB). A `LIMIT 10`
query on small files costs a negligible amount, but an unbounded `SELECT *`
on the full 1.1 GB Lending Club file would scan the whole file each time —
worth remembering for any heavier exploration later.
